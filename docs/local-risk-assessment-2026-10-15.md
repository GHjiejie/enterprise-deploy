# 企业定制构建本地风险评估

检查日期：2026 年 10 月 15 日，Asia/Shanghai。

`qianshi` 配置仅开放视频模块，但本地 production 和 staging 交付包均保留了对话、图片生成、模型广场的编译实现。在临时副本中，仅修改内置模块开关就能恢复对话和图片生成页面。当前企业开关有效控制正常页面入口，尚不能满足“交付包只包含已开放模块专属代码”的要求，也不能承担真实业务能力的安全授权。

## 风险与整改优先级

以下优先级面向企业代码交付要求，不是 CVSS 评分。当前页面尚未接入真实业务服务，本次没有确认真实 API 越权、数据泄露或服务端授权失效。

| 编号 | 已确认的问题                 | 优先级与适用条件                 | 影响                                                              |
| ---- | ---------------------------- | -------------------------------- | ----------------------------------------------------------------- |
| R01  | 关闭模块的专属实现仍被交付   | 高，要求只交付开放模块代码时     | 客户可获取、阅读和复用未开放模块的编译代码                        |
| R02  | 修改前端包可以恢复隐藏界面   | 高，试图用前端开关保护功能权益时 | 客户自有环境中的页面限制可被绕过；实际 API 是否可用仍由服务端决定 |
| R03  | 图片逻辑保留在视频共用组件中 | 中，属于 R01 的整改依赖          | 仅删除图片页面入口仍可能残留图片专属分支                          |
| R04  | 当前验收未验证禁用代码不存在 | 中，要求代码物理裁剪时           | 页面与摘要测试通过，仍可能把禁用代码交给客户                      |

### R01 关闭模块的专属实现仍被交付

两份产物的 `assets/` 中都存在以下页面文件：

| 模块         | production 文件    | staging 文件       | 内容证据                                              |
| ------------ | ------------------ | ------------------ | ----------------------------------------------------- |
| 智能对话     | `page-DOnOlEPz.js` | `page-CuybFasn.js` | `chat-page`、问题输入框、表单提交逻辑、“检查对话输入” |
| 图片生成入口 | `page-CiFFNmwq.js` | `page-CQGB9UkV.js` | 导入创作页并以 `kind: image` 渲染                     |
| 模型广场     | `page-CyB3MJ1P.js` | `page-BMaSQu_M.js` | `catalog-page`、模型卡片、搜索与历史入口              |
| 视频生成入口 | `page-CsTDLBU_.js` | `page-BNrIJXSc.js` | 导入创作页并以 `kind: video` 渲染，属于本企业开放模块 |

生产主入口 `index-Do4F9HLv.js`、预发布主入口 `index-CD0SruBc.js` 都保留对四个页面的动态导入。上述结论基于实际页面实现与依赖引用，不只是文件名或关键词命中。

原因见 [app.tsx](../src/app/app.tsx)：`pages` 对所有模块声明 `lazy(() => import(...))`，运行时才根据企业配置决定渲染哪个页面。懒加载控制请求时机，不会自动把关闭模块从构建依赖图删除。原[架构方案第 8 节](architecture.md#8-关闭模块与物理裁剪)和 README 已明确初版只承诺行为关闭；本项记录的是当前能力与“禁止交付禁用代码”要求之间的差距。

整改应在构建阶段按已校验配置生成仅包含已启用模块的装配入口，并让业务应用只依赖该入口。生成入口应按构建隔离，避免修改公共源码后被其他企业构建复用。不应通过打包后手工删除 JS 文件处理，主入口及其依赖可能仍然引用这些文件。

### R02 修改前端包可以恢复隐藏界面

受控验证使用 production 产物的操作系统临时副本，仅修改主入口中内置配置的三个关闭模块开关为 `true`，其余页面实现保持原样。原产物与副本分别通过本地 HTTP 服务访问，浏览器结果如下：

| 路径                | 原产物            | 修改后的临时副本    |
| ------------------- | ----------------- | ------------------- |
| `/chat`             | `route-not-found` | `chat-page` 可见    |
| `/playground/image` | `route-not-found` | `image-studio` 可见 |

验证结束后临时文件、浏览器及临时 HTTP 服务已清理，原产物摘要保持一致。临时副本没有重算或修改发布清单，也没有通过 `release:deploy` 部署；本结果证明浏览器端界面可恢复，不证明发布校验被绕过。

[features.ts](../src/platform/features.ts) 中的 `Object.freeze` 用于防止应用运行过程中的意外赋值，不能限制持有静态文件的人在执行前修改 JavaScript。客户也可以修改前端路由或重新编写界面，因此即使代码裁剪完成，真实业务能力仍应由服务端独立授权。OWASP 建议在服务端等可信位置执行授权，并逐请求验证权限。[授权检查依据](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#verify-that-authorization-checks-are-performed-in-the-right-location)

整改要分别处理两类目标：通过构建裁剪减少未开放实现的暴露；通过可信登录身份、企业关系和服务端能力策略保护真实操作。是否禁止图片 API 能力需要独立产品约定，不能从“关闭图片体验页面”自动推导。

### R03 图片逻辑保留在视频共用组件中

production 的 `studio-page-4ekoWoYj.js` 和 staging 的 `studio-page-Cgxi8YMd.js` 都保留图片与视频分支。源码 [studio-page.tsx](../src/shared/studio-page.tsx) 接受 `kind: 'image' | 'video'`，根据参数渲染不同标题和创作描述。

这是 R01 的另一条依赖路径。仅移除图片页面的动态导入，不足以证明图片专属实现已经清除。应把模块专属行为放回对应模块，或在构建时固定参数并通过依赖和实际输出检查确认分支被消除。

公共上传、预览和表单能力可以继续共享。不能把所有包含 `image` 的代码都判为图片生成模块，也不能误删对话中的图片理解、文件上传或视频模块仍需要的公共组件。

### R04 当前验收未验证禁用代码不存在

[交付浏览器测试](../tests/delivery/browser.spec.ts) 当前验证关闭模块的路径显示页面不存在、管理员不能打开模块，以及页面请求未加载相关 `page-*` 代码块。这些测试验证了正常入口行为，没有断言代码块不在磁盘或交付包中。

[发布记录校验](../build/release-record.ts) 检查企业、环境、配置与文件摘要一致。清单根据实际输出生成，正确包含禁用代码的包也可以通过完整性校验；它没有验证每个输出模块是否属于本企业允许交付的范围。

应新增单独的物理裁剪验收，结合构建依赖信息、模块资源归属与实际输出清单核对禁用模块的专属实现和资源。模块名、文件名或文案搜索可以辅助定位，不能作为唯一依据。命令行构建、可视化打包、交付归档应使用同一条验收链路。

## 已生效控制与生产接入条件

原包的企业配置和正常路由控制有效，以上原包浏览器对照显示关闭页面无法进入。配置、装配与制品完整性校验也已生效。两份包中没有 `.tsx`、`.ts` 原文件或 `.map`，但编译后的 JavaScript 仍包含业务实现。

生产接入还需要处理以下已知边界，它们不代表本次已经发现真实服务漏洞：

- [permissions.ts](../src/platform/permissions.ts) 使用明确标记的 `DEMO_ACCESS`，页面提供演示角色切换，默认选择完整权限的演示用户。正式应用需要接入可信身份和权限数据，并移除演示身份入口；演示角色不是安全认证。
- 当前对话和生成页只实现演示 UI 与输入校验，未连接真实业务服务。恢复页面不能据此证明可以生成图片、消耗模型额度或访问他人数据；接入后端后要另行验证越权与企业隔离。
- `demo-qianshi-*.json` 仅为演示兼容声明，不代表后端已经关闭某项能力。实际授权以服务端可信策略为准。
- SHA-256 清单用于检查一致性，不是数字签名。有权同时替换文件和清单的人可以重新计算摘要；可信交付仍依赖受控 CI、制品库和部署权限，按交付需求增加独立签名校验。

## 整改验收要求

| 目标           | 通过条件                                                                                           |
| -------------- | -------------------------------------------------------------------------------------------------- |
| 正常入口控制   | 视频正常进入；关闭模块的菜单、快捷入口、规范路径、别名及详情路径仍不可用                           |
| 禁用代码不交付 | `qianshi` 的依赖图、静态包及下载包均不含关闭模块的专属页面、初始化、请求与资源；公共依赖有明确归属 |
| 共享能力保留   | 视频必需公共能力仍工作；其他企业已开放模块回归通过                                                 |
| 真实业务授权   | 如果产品要求禁止某能力，直接请求真实接口也由服务端拒绝；修改前端开关不能授予权限                   |
| 自动验收       | CLI 与控制台构建均执行裁剪检查，发现禁用专属实现或资源时阻断交付                                   |
| 制品一致性     | 重建后更新发布记录，预览、下载包、归档和部署对应同一企业、环境与文件摘要                           |

整改顺序建议先明确模块专属实现及公共依赖的范围，再完成按配置的构建入口和共享逻辑拆分，补充物理裁剪检查，最后重建并检查每个实际交付配置。服务端授权应在真实业务接入时同步落实，不能以完成前端裁剪作为替代。

## 复核方式

以下命令读取现有产物，不会触发重新构建：

```bash
# 查看内置交付配置和当前包内的相关页面实现
cat config/profiles/qianshi.json
rg --no-ignore -l 'chat-page|catalog-page|kind:`image`|kind:`video`' dist/qianshi/production/assets

# 核对原产物的身份与完整性
npm run release:verify -- --profile qianshi --mode production --artifact dist/qianshi/production --backend-policy config/backend-policies/demo-qianshi-production.json
npm run release:verify -- --profile qianshi --mode staging --artifact dist/qianshi/staging --backend-policy config/backend-policies/demo-qianshi-staging.json
```

关键词定位之后仍需读取页面实现和主入口依赖。临时副本恢复界面的对照与原产物完整性校验是两项独立验证，不能把其中一项的结果扩展成真实后端授权结论。
